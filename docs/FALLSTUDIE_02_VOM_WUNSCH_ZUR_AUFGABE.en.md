# Case study 02: From a request to a traceable task

[Deutsch](FALLSTUDIE_02_VOM_WUNSCH_ZUR_AUFGABE.md) · [English](FALLSTUDIE_02_VOM_WUNSCH_ZUR_AUFGABE.en.md)

**JOLIBEN · Thiemo Gerhardt, Initiator & Product Owner**  
**Documented case: 19 October 2026 · Editorial version: 22 October 2026 · English edition: 23 October 2026**

## The case in one minute

An existing area of the software in my own development project was to be reviewed. A short request became an AI-generated plan. After a visible review of data use and costs, a deliberate choice of project and explicit confirmation, the plan became a task. The original plan and its provenance remained traceable within that task.

This documented a concrete transition from planning to task creation. The subsequent substantive review and a completed findings report are outside the demonstrated outcome of this case. That transition raised the next product question: Does the task that has been created already match the type of work and result actually wanted?

## 1. A short request needs a clear assignment

For this public account, the request can be expressed as follows:

> Review an existing area of the software and summarise the findings in a report. Changes to the system are outside the scope of this review request.

This is an editorially simplified account of the documented internal review case, not a verbatim user quotation or a client commission. The underlying test concerned an existing area of my own development project.

A request like this opens up several decisions: Which context is relevant? Which data will be used for planning? What result should be produced? Which project does the task belong to? And what work will actually be authorised afterwards?

JOLIBEN is intended to make these decisions understandable and preserve the relationship between the request, the plan and the task. This case shows one part of that path that has been tried in practice.

## 3. Three decisions with different effects

| Decision | What it means | Scope in this case |
| --- | --- | --- |
| **Allow planning** | Review the selected context and the decision on data use and costs for the AI step concerned | Part of the planning flow shown in the browser |
| **Create a task** | Deliberately confirm the project assignment and task creation | Documented for the assignment examined |
| **Authorise the work** | Separately define the appropriate type of work and the limits that apply to it | The substantive work on the review request was neither authorised nor performed in this case |

This separation is a product decision. A created task records what the work concerns and what it is based on. What work may take place afterwards remains a separate decision.

## 4. The concrete result

At the end of the demonstrated part of the process, an actual task existed with a traceable source plan. The review of the existing state on 19 October 2026 confirmed the task and its associated original plan. The context update describes the browser flow shown as successful.

For this case, it was therefore possible to trace:

- The request that provided the starting point.
- The plan on which task creation was based.
- The project to which the task was assigned.
- That the original source was preserved and could be read within the task.
- That substantive execution remained a separate step.

This is concrete evidence of the transition from planning to task creation. It does not claim that the project area was fully reviewed or that a completed findings report was saved.

## 5. The main insight emerged at the next handoff

To produce the requested review report, the next stage needed to be prepared appropriately as a read-only investigation. The existing handoffs examined did not yet demonstrate that complete path. The outcome criteria also needed to match the requested report.

This gave rise to a new product requirement: The original plan should remain traceable, while a more precise assignment explicitly describes the type of work, its result and its acceptance criteria. Such clarification must not silently replace the original source plan.

| Requirement for the next step | Design objective | Status |
| --- | --- | --- |
| **Clarify the result** | Define the findings and evidence the requested report should contain | Further clarification and implementation required |
| **Choose the appropriate type of work** | Explicitly distinguish a read-only review from implementation that makes changes | A completed end-to-end path has not yet been demonstrated for this assignment |
| **Preserve provenance** | Keep the original plan visible and make new criteria separately traceable | The original plan is preserved in this case; further clarification remains development work |

The quality of AI-assisted collaboration therefore also depends on whether handoffs are clear in terms of the work to be done. The case study shows how a completed intermediate step can reveal the next concrete product requirement.

## 7. What the evidence supports and what remains open

**Documented:** the selected planning and task-creation flow, an actual task, its deliberate project assignment, and the preserved, readable original source.

**Open:** the complete path to a finished read-only review report; application to other types of assignment; more reliable conclusions about context quality and recovery in different failure scenarios.

Better plan quality was observed in one individual comparison. This does not establish a general improvement in quality. Time savings, economic benefit, general reliability and a complete autonomous end-to-end process were neither measured nor demonstrated for this case study.

## 8. Transferability as a design approach

The principle is relevant to projects in which AI proposals are intended to become binding work assignments. For example, a department could request a review of an existing process and define the goal, result and responsibility before further work begins.

This is a possible application scenario, not a client case that has already been carried out. Suitability for a particular organisation and its tasks would need to be assessed separately.
